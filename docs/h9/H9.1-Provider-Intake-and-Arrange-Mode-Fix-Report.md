# H9.1 — Provider Intake and Arrange-Mode Fix Report

Sprint: H9.1 · Mode: BUILD · Scope: presentation layout fix + provider intake
Status of prior work: H4–H9 preserved. No certification was run. No schema, migration, CI, or certification semantics changed.

---

## 1. Root cause of arrange-mode overlap — **validated**

Two independent causes, both in `src/features/home/components/service-shelf.tsx`:

1. **The grid did not share a row height.** The shelf used `sm:items-start`, which
   stops grid items from stretching. Each tile then sized itself independently,
   so the tallest tile in a row (the one whose brand name wraps) set the row box
   while shorter tiles ended above it — the arrange control strip of a tall tile
   sat visually against the row below. `sm:items-start` *was* present in the
   emitted CSS; the reported "not taking effect" symptom was this alignment
   behaviour, not a missing utility. (**corrects the H9 hypothesis**)
2. **The control strip could not shrink or wrap.** Four 32px controls plus gaps
   need ~140px. At `sm` (4 columns) and inside the 144px mobile rail this is at
   or beyond the tile width, and the strip had neither `flex-wrap` nor
   `shrink-0` children, so it overflowed the tile box.

The inner button also carried `h-full`, a percentage height against an
auto-height parent, which resolves to `auto` and contributed nothing.

## 2. Layout fix implemented — **product-facing, validated**

- Shelf list: `sm:items-start` → `sm:items-stretch sm:auto-rows-auto`, plus
  `items-stretch` on the mobile rail. Rows now grow with their tallest tile.
- Tile (`li`): `h-full min-w-0` so the tile fills its stretched row and its text
  may truncate rather than push.
- Tile button: `h-full` → `grow`, so the button absorbs spare height and the
  control strip is pinned to the bottom of the tile.
- Control strip: `flex-wrap`, and every control is `shrink-0`; strips wrap to a
  second line rather than overflow. Added `data-sf-arrange-controls` and
  `data-sf-service-tile` hooks for measurement.

Measured with a headless browser over the exact class composition at **375, 390,
768, 1280 px**: every control strip is fully inside its tile box
(`controls.bottom ≤ tile.bottom`, `controls.right ≤ tile.right`) and no tile's
controls intersect a tile starting below it. Controls remain 32px targets inside
a 36px-min row. Move / pin / hide / reset behaviour is untouched (no handler,
domain function, or persistence changed).

## 4. Capability classification — **validated against the code, not marketing**

All four are **launch-only**:

- `playbackControlMode: "launch-only"`, `allowsEmbeddedPlayback: false`,
  `requiresOwnSubscription: true`, `requiresProviderLogin: true`.
- Rationale: ADR-014 stands. StreamFlow may open a public provider URL in the
  member's own browser and coordinate people around it. There is no permitted
  play/pause/seek path for any of these services, so `controllable` is not
  available to any of them. `unavailable` would be wrong because the handoff and
  room coordination genuinely work.

None is labelled `controllable`. A test asserts this for all four.

## 5. Homepage migration behaviour — **validated**

`normalizeLayout` already reconciles a stored arrangement against the current
app set: pins and hides are kept, deliberate order is kept in place, and apps
that appeared since the arrangement was saved are appended after everything the
person placed — visible, never arriving pre-hidden. Tests cover a customized
shelf (one pin, one hide, reordered remainder) surviving the arrival of the four
brands with pins, hides, and relative order intact, and a hidden new provider
remaining reachable through the hidden ("more apps") list.

## 6. Analytics changes — **none required**

The existing event vocabulary already covers this sprint: `provider_selected`,
`provider_launch_clicked`, `manual_sync_requested`,
`favorites_used_for_selection`, and the H9 personalization events. New providers
flow through them by their provider key only. No credential, cookie,
subscription detail, or private media identifier is recorded.
`provider_added_to_catalog` was deliberately **not** added: the catalog is
curated data, not something the app writes, so the event would have no honest
emitter (**development-only note**).
