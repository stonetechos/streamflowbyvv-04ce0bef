## 1. Executive summary

All ten frozen M1 work packages (WP1–WP10) have implementation reports and are complete as _work packages_. M1 is nevertheless **not** ready for Final Certification Execution, for two distinct reasons:

1. **Three rows are openly incomplete** — `CERT-EXP-01` (Unmeasured, manual audit), `CERT-PROV-02` (Unmeasured, harness), `CERT-SYNC-C-02` (Blocked, environment/governance). This was already known and reported at WP8/WP9/WP10.
2. **A retention/traceability finding surfaced by this review (Finding R1):** no single run in the repository holds a passing record for every M1 row, and the runs cited as sealed passes for `CERT-ROOM-01…04`, `CERT-WP-01/02` (`RUN-M1WP3-001`, `RUN-M1WP4-001`, `RUN-M1WP6-001`, also `RUN-M1WP5-001`, `RUN-M1WP7-001`, `RUN-M1WP8-001`) **are not present in the current tree**. `tests/certification/evidence/` contains exactly three runs: `RUN-M0R-001`, `RUN-M1WP9-001`, `RUN-M1WP10-001`. In the most recent broad run, `RUN-M1WP9-001`, those six room/watch-party rows are recorded `unmeasured` ("certification identities or a lobby could not be provisioned in this environment").

Consequence: judged on **repository truth as it stands today**, six further M1 rows are Unmeasured in the newest available evidence, not merely the three named rows. This is documented, not remediated.

The product's _honesty posture_ is the strongest part of the package: capability disclosure, Tier C framing and ADR-014 conformance are backed by passing automated evidence on both the selection and launch surfaces. The weakness is measurement retention and environment coverage, not overclaim.

## 5. CERT-EXP-01 — detailed review

- **Current state:** Unmeasured (`RUN-M1WP10-001`, chromium, PROF-09).
- **Why incomplete:** the row is "WCAG 2.1 AA on all launch surfaces". Automation covers only 4.1.2 (name/role/value), 3.1.1 (language) and 2.4.2 (title). Contrast, focus order and screen-reader behaviour are manual under PROF-09 per `docs/blueprint/K-launch-certification.md`. WP10 correctly refused to promote on automation alone.
- **Product implementation sufficient?** Unknown. The automatable subset is clean on all 13 measured surfaces; the manual subset has never been measured, so sufficiency cannot be asserted.
- **Blocker type:** Manual audit.
- **Exact evidence available:** `RUN-M1WP10-001/records/CERT-EXP-01.json` (unmeasured) plus five `CERT-A11Y-*` chromium passes for `/`, `/auth`, `/auth/sign-in`, `/auth/sign-up`, `/auth/forgot-password`. No manual evidence of any kind exists in the repository.
- **Smallest next action:** perform the PROF-09 manual audit (contrast ratios, focus order, screen-reader pass) across the 13 launch surfaces and record the result as manual evidence.
- **Requires code changes?** No — unless the audit itself finds defects.
- **Allowed before final certification?** Yes; it is a prerequisite to it, and it is a governance/audit activity, not implementation.
- **Release impact:** blocking. An accessibility claim cannot be made, and the Launch Certification checklist cannot close.

## 6. CERT-PROV-02 — detailed review

- **Current state:** Unmeasured (`RUN-M1WP9-001`, PROF-01).
- **Why incomplete:** the row requires "one-step fallback, announced, reversible". Measuring it requires injecting a provider-launch fault and observing the announced, reversible alternative. No fault-injection seam exists on the provider launch path, and the profile mapping for that run is still `Needs discovery` in the frozen M1.1 discovery document.
- **Product implementation sufficient?** Unknown. Fallback copy and classes exist (WP7/WP9 work), but fallback _behaviour under fault_ has never been exercised.
- **Blocker type:** Harness (with an unresolved discovery/governance input on the profile mapping).
- **Exact evidence available:** `RUN-M1WP9-001/records/CERT-PROV-02.json` (unmeasured, with the blocker named). No positive or negative fallback measurement exists.
- **Smallest next action:** resolve the `Needs discovery` profile mapping, then add a test-only fault-injection seam on the provider launch path so the existing spec can drive it.
- **Requires code changes?** Yes — a seam, at minimum in test infrastructure and probably a narrow product hook.
- **Allowed before final certification?** Only under a new authorized work package. It is explicitly out of scope for this review sprint and was not performed.
- **Release impact:** blocking for any claim of graceful provider fallback.

## 7. CERT-SYNC-C-02 — detailed review

- **Current state:** Blocked (`RUN-M1WP9-001`, PROF-01).
- **Why incomplete:** the row is "as `CERT-SYNC-C-01`, on web-mobile". `playwright.config.ts` has no `web-mobile` project, so the row has no execution environment; it ran under `web-chromium`, which cannot satisfy a mobile platform claim. A second, independent unknown: the I.13 governance position on web-mobile within the Launch Envelope.
- **Product implementation sufficient?** Yes, as far as can be determined — the measurement is implemented and runs unchanged once a mobile project exists; `CERT-SYNC-C-01` passes on the identical logic.
- **Blocker type:** Environment, compounded by Governance.
- **Exact evidence available:** `RUN-M1WP9-001/records/CERT-SYNC-C-02.json` (blocked, blocker named), plus the passing desktop sibling `CERT-SYNC-C-01`.
- **Smallest next action:** obtain the I.13 governance ruling on whether web-mobile is inside the M1 Launch Envelope; if yes, add the `web-mobile` Playwright project.
- **Requires code changes?** Configuration only (a Playwright project), no product change.
- **Allowed before final certification?** The governance ruling is allowed and required; the configuration change needs its own authorization. Neither was done here.
- **Release impact:** blocking only if web-mobile is inside the released envelope. The frozen Launch Envelope is "web desktop first", so a governance ruling could legitimately scope this out of M1 — that ruling does not exist in the repository, so the row stays Blocked and is **not** interpreted away.
