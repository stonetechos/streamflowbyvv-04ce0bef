## Repository Recovery Analysis

### Method

1. `git ls-tree -r HEAD tests/certification/evidence` — current tree.
2. `git log --all --diff-filter=A --name-only -- 'tests/certification/evidence/*'` — every addition of any evidence path on any reachable ref.
3. `git rev-list --all --objects | grep 'RUN-M1'` — exhaustive object-level search for M1 run paths.
4. `git ls-tree -r be5c440` and `git ls-tree -r f1ae897` — the two revisions M1.13/M1.14 discuss.
5. `git tag`, `git branch -a` — alternative preservation refs.
6. `git log -L` on the `.gitignore` evidence line — when the exclusion took effect.

### Findings

- **Current tree** contains exactly one run directory: `tests/certification/evidence/RUN-M0R-001` (index, records, `artifacts/.last-run.json`). No `summary.json`, no `completed.json` — consistent with M1.14.
- **Reachable history** contains evidence additions only for `RUN-M0R-001` and a family of auto-derived M0-era runs named `RUN-<yyyymmddThhmm>-<commit>` (e.g. `RUN-20260806T0636-0dd9c38`, `RUN-20260806T0637-cc64e1f`, `RUN-20260806T0638-0623e19`, `RUN-20260806T0638-1c75040`), added at commits `0dd9c38`, `cc64e1f`, `0623e19`, `1c75040`, `ca4cb39`, `8463729` — all **before** the ignore rule at `20f0691` and all containing **M0-era rows only** (`CERT-AUTHZ-*`, `CERT-PERF-*`, `CERT-SA-*`, `CERT-RES-*`, `CERT-VOICE-*`, `CERT-A11Y-*`, `CERT-PROV-A1-*`). None contains a single M1 row (`CERT-ROOM-*`, `CERT-WP-*`, `CERT-EXP-*`, `CERT-PRES-*`, `CERT-PROV-01/02`, `CERT-SYNC-C-*`).
- **Object-level search** for `RUN-M1` across all refs: **no matches**. Confidence: high — this is an exhaustive scan of the reachable object graph, not a path or tree sample.
- **Tags:** none exist (`git tag` empty). **Branches:** `main`, `origin/main`, and the current edit branch — none carries an M1 evidence path.
- **RUN-M1WP1-001 does not exist and never did.** WP1 was the harness-construction sprint (`docs/m1/M1-Backlog.md` §WP1); it produced spec homes, fixtures and instrumentation, not a sealed run. `docs/m1/M1.4-WP2-Implementation-Report.md` onwards is where run IDs begin. The mapping is recorded in the matrix below rather than treated as a missing artifact.

Two requirements the brief asks about are **not defined anywhere in the frozen authorities**, and are recorded as gaps rather than answered by invention:

- **No explicit recovery rule.** The authorities define sealing, immutability and refusal; they are silent on what to do when an artifact never existed.
- **No explicit statement that missing evidence invalidates prior certification claims.** What the authorities do state (`Evidence-Guide.md:36–44`, `tests/certification/README.md` rule 1) is that a row without an executed, threshold-satisfying record is not a pass. The operative consequence is therefore not "invalidation" but **non-promotion**: the claims in `docs/m1/M1.4`–`M1.12` remain accurate _descriptions of executions that occurred_, while being **unsubstantiated as certification** in the current tree. This report does not rewrite those reports.
- **Unsealed or partial evidence may not be used.** `scripts/evidence.mjs` refuses the seal and writes `complete: false`; `RUN-M0R-001` lacking `summary.json`/`completed.json` is therefore not usable as a certification basis.

- **Risk:** none applicable.

### Option B — Recover artifacts from reachable historical commits

- **Prerequisite:** an M1 evidence blob reachable from any ref.
- **Evidence needed:** an object-graph hit for `RUN-M1*`.
- **Affected rows:** all 14 M1 rows.
- **Source-code changes required:** none.
- **Certification semantics change:** none.

- **Preserves historical claims:** would have, fully.

- **Recommendation: not viable.**

### Option C — Recover artifacts from CI or external retention

- **Prerequisite:** the runs executed in CI, and a repository-verifiable reference (workflow run id / artifact name) exists within the 90-day window.
- **Evidence needed:** a committed `RUN-CI-<run_id>-<attempt>` instance cited by an M1 report.
- **Affected rows:** all 14 M1 rows.
- **Source-code changes required:** none.
- **Certification semantics change:** none, if provenance is intact.
- **Governance approval:** would be required to admit externally-held artifacts as repository evidence.
- **Preserves historical claims:** would have.
- **Risk:** admitting an unverifiable pointer as evidence; the frozen rules forbid prose or a URL standing in for a record.
- **Feasibility:** every M1 run used `CERT_ENVIRONMENT=local-dev` and was executed locally. No M1 report cites any CI run id or URL. CI artifacts for these runs **cannot exist**. External verification unavailable; no external recovery is claimed.
- **Recommendation: not viable.**

### Option D — Fresh certification execution using existing implementation

- **Prerequisite:** implementation unchanged and present (**satisfied** — WP1–WP10 source and harness are tracked at `HEAD`); a working three-engine browser environment (**not currently satisfied** — Firefox and WebKit binaries are unavailable, and Chromium has required a manual wrapper); a durable retention path so the run survives (**not currently satisfied** — RET-1).
- **Evidence needed to justify it:** Options A, B and C shown not viable on repository facts — established above.
- **Affected rows:** all 14 M1 mandatory rows, in a single full-matrix run (GATE-01 refuses partial seals).
- **Source-code changes required:** **none.** The certification procedure runs against the implementation as-is.
- **Certification semantics change:** **none.** New RUN-IDs, new evidence, no claim of historicity.
- **Governance approval required:** **yes** — a Build Mode / human execution gate per `docs/blueprint/I-governance.md`. No ADR is required, because nothing architectural changes.
- **Preserves historical claims:** **no.** The WP reports remain accurate narratives; the new run is new evidence at a new commit and must not be presented as recovery of `RUN-M1WP2-001`…`RUN-M1WP10-001`.
- **Risk:** (i) a fresh run may legitimately produce different results from the narrated ones — that is a feature, not a defect; (ii) if RET-1 is unresolved, the fresh run is lost exactly as its predecessors were; (iii) the three named open rows will not clear by execution alone.
- **Feasibility: high on implementation, blocked on environment and retention prerequisites** — both of which are identified here and neither of which is remediated by this sprint.
- **Recommendation: viable, subject to the named prerequisites.**

### Option E — Other repository-supported options

- **E1 — Accept `RUN-M0R-001` as partial substitute.** Not viable: unsealed, zero M1 rows, registry-incompatible with `required-evidence.json` v1.1.0. Explicitly rejected by the sprint brief and by GATE-01.
- **E2 — Reconstruct evidence from the WP implementation reports.** Not viable and **not permitted to be called recovery** under the sprint's definitions. Reports are prose; `tests/certification/README.md` rule 1 and `Evidence-Guide.md:36–44` forbid promoting a non-executed row.
- **E3 — Retention repair as a precondition to any execution path.** Repository-supported in principle (RET-1 is a real, cited configuration conflict) but **out of scope**: `.gitignore` and retention configuration are explicitly protected this sprint. Recorded as the first prerequisite of Option D, not as an alternative to it.
- **E4 — Declare M1 certified on implementation completeness alone.** Not viable: directly contradicts `Evidence-Guide.md`, GATE-01, and the project's standing anti-overclaim posture.
- **Recommendation: not viable as standalone paths.** E3 is retained as a prerequisite of Option D.

## Recommended Path

**Option D — a fresh certification execution against the existing, unchanged implementation.** In the brief's final-decision vocabulary this is statement **C**.

- **Repository facts:** one run directory exists; it is `RUN-M0R-001`; it is unsealed and pre-M1.

- **Constitutional facts:** sealing, immutability, derived run identity, mandatory-evidence GATE-01 and the status vocabulary all permit a fresh run and all forbid promoting an unevidenced row. No authority forbids recertifying unchanged implementation, and no ADR is triggered because nothing architectural changes.
- **Row-level impact:** all 14 M1 rows require fresh execution; three of them (`CERT-EXP-01`, `CERT-PROV-02`, `CERT-SYNC-C-02`) will not be cleared by execution alone and remain separately blocked.

Prerequisites to be satisfied **before** any such execution is authorised — none of them performed here:

2. Provision a working three-engine browser environment, or accept honestly-recorded engine-scoped `blocked` rows.

4. Keep `CERT-EXP-01` (manual PROF-09 audit), `CERT-PROV-02` (fault-injection seam), `CERT-SYNC-C-02` (web-mobile project + I.13 governance) open under their own authorisations.
